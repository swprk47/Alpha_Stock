# 스윙 추천 규칙 백테스트 설계

작성일 2026-11-02 · 브랜치 `feat/backtest-design`(설계 문서 먼저, 구현은 승인 뒤 별도 PR)

## 1. 목적과 사용자 결정

장이 열린 시간에 추천이 거의 안 나오는 문제를 조사하다가, 추천을 거르는 전략(`strategy.py`의 `analyze_stock_for_swing`)과 익절·손절 규칙이 **한 번도 과거 데이터로 검증된 적이 없다**는 점이 드러났다. 사용자는 코드를 먼저 고치기보다 "지금 앱 규칙이 타당한지부터 보고, 개선안이 있으면 그다음에" 하기로 했다. 실제 개인계좌 투자에 참고하는 앱이라 추측이 아니라 과거 데이터로 확인한다.

| 결정 | 내용 |
|---|---|
| 이번 단계의 질문 | **현재 규칙(추천 조건 + 익절 +6.5% / 손절 -3.0% / 5영업일)이 과거에 타당했는가**. 개선안 비교는 기준선이 나온 뒤 |
| 성공 기준 | 앱 규칙 그대로. 5영업일 안에 +6.5%에 먼저 닿으면 성공, -3.0%에 먼저 닿으면 실패, 둘 다 아니면 5일째 종가로 정리한 손익 |
| 매수 가정 | **두 가지 모두 실행**: ① 신호일 종가 매수 ② 다음 거래일 시가 매수 |
| 접근 | **A**: 앱의 실제 `analyze_stock_for_swing`을 그대로 호출하는 오프라인 도구. 점수 계산을 다시 구현하지 않는다 |
| 단위 | 이번 1단계는 **신호 단위 통계**. 예산 구간별 자산 곡선 같은 포트폴리오 시뮬레이션은 2단계 |
| 코드 범위 | 새 `backtest/` 폴더만. 앱 코드는 읽기만(import). `strategy.py` 수정 없음 |

범위 밖: 장중 거래량 문제(일봉으로 재현 불가), 포트폴리오 시뮬레이션, 개선안 비교(기준선 이후), 화면 표시, 서버 API, 실거래 연동.

## 2. 확인한 사실 (설계 근거)

모두 2026-11-02에 직접 확인했다.

| 사실 | 근거 |
|---|---|
| 일봉은 최대 3,000개(삼성전자는 2014-08 ~ 2026-11, 12년)까지 받아진다 | 네이버 차트 API `count=3000` 호출 |
| 가격은 액면분할이 반영돼 있지만 **거래량은 반영돼 있지 않다** | 삼성전자 2018-05-04 분할: 종가 53,000 → 51,900로 이어지고 거래량은 606,216 → 39,565,391. 거래정지일 거래량 0 |
| 앱은 **최근 60봉**으로 분석한다 | `get_stock_daily_candles(code, count=60)`, 지표는 모두 롤링 윈도우(`ma5/20/60`, `rsi14`, `bb`) |
| 실제 분석 함수 호출은 1회 약 3.2ms | 삼성전자 300회 호출 0.96초. 300종목 x 2,900일(약 87만 회)은 1프로세스 약 46분, 8코어 병렬이면 몇 분 |
| 후보 풀은 **시가총액 순서**로 앞 30개다(거래대금 순이 아님) | `get_market_candidate_stocks`: 네이버 시총 목록 3쪽(150개)씩 코스피 먼저, 코스닥 순으로 읽고 `candidates[:30]` |
| 후보 조건 | 가격 1,000원 이상 ~ 예산 구간 상한 이하, 오늘 누적 거래대금 20억 이상, 거래 가능 상태 |
| 추천은 점수 60 이상만 | `analyze_stock_for_swing`의 `score >= 60`. 정렬은 (점수, 손익비), 화면은 상위 3개 |
| 예산 구간 | 1만·2만·5만·10만·20만·50만·100만… (`recommendation_cache.BUCKETS`). 구간 하한으로 후보를 뽑는다 |
| 수수료·세금은 설정값 | 매수 0.015%, 매도 0.015%, 매도 세금 0.20% (`config`, `/api/trade-rules`) |

## 3. 구성과 데이터 흐름

저장소 루트의 `backtest/`에 앱과 분리해서 둔다. 각 조각은 한 가지 일만 한다.

| 조각 | 하는 일 | 의존 |
|---|---|---|
| `data.py` | 오늘의 시총 상위 목록(코스피 150 + 코스닥 150, 순서 유지)과 종목별 일봉 3,000개를 받아 로컬 캐시(`backtest/cache/`)에 저장. 분할·거래정지 구간 표시 | 앱 `market_data` |
| `pool.py` | 날짜 t마다 앱의 후보 선정 규칙을 과거 일봉에 적용(앞 30개) | `data.py` |
| `signals.py` | 후보마다 **`strategy.analyze_stock_for_swing`을 그대로 호출**(날짜 t까지 최근 60봉 창, `current_price` = t의 종가). 함수는 인자로 받아 나중에 개선안을 끼워 비교 | `strategy` |
| `simulate.py` | 신호마다 매수·익절·손절·만료를 시뮬레이션하고 비용 반영 | 앱 `config` |
| `report.py` | 지표, 연도별, 민감도, 대조군, 마크다운·CSV·JSON 출력 | |
| `run.py` | `python -m backtest.run`으로 위를 이어 실행(8코어 병렬, 중단 후 이어하기) | |

흐름: `일봉 캐시 → 날짜별 후보 풀 → 신호 → 거래 시뮬레이션 → 보고서`.

`backtest/cache/`와 `backtest/results/`는 `.gitignore`에 넣는다(내려받은 시세 데이터와 실행 결과). 새 외부 의존성은 추가하지 않는다(`pandas`는 이미 사용 중).

## 4. 후보 풀과 추천 선정

날짜 t마다:
1. 오늘의 시총 순서(코스피 먼저)로 종목을 훑어, t의 종가가 1,000원 이상 ~ 예산 구간 상한 이하이고, t의 거래대금(종가 x 거래량)이 20억 이상이며, t에 거래정지가 아닌 종목을 **앞에서 30개** 모은다.
2. 예산 구간은 **10만, 20만, 50만 원** 세 개로 돌린다(구간 상한이 후보 풀의 가격 상한).
3. 후보마다 분석 함수를 부르고 **60점 이상**인 종목을 (점수, 손익비) 내림차순으로 정렬한다.
4. **그날의 추천 = 상위 3개**(앱이 화면에 보이는 것과 같다). 통과한 전체를 보는 보조 집계도 함께 낸다.

한계(보고서 맨 위에 명시): 후보 풀의 시총 순서는 **오늘 기준 목록**이라 과거 시점의 시총 순위와 다르고, 이미 상장폐지된 종목은 빠진다(생존 편향). 과거 시점 순위는 구할 수 없다. 또 가격은 분할이 반영돼 있고 거래량은 아니라서 분할 전에는 실제 가격이 더 높았으므로, 분할이 감지된 종목은 **마지막 분할 이전 기간을 후보 풀에서 뺀다**(그 시기의 예산 구간 조건을 믿을 수 없다).

## 5. 매수와 청산 규칙

**매수**(두 가지 모두 실행)
- ① 신호일 t의 종가에 매수 → 청산 판단은 t+1부터.
- ② 다음 거래일 t+1의 시가에 매수 → 청산 판단은 t+1의 장중부터.
- 같은 종목이 보유 중에 다시 신호가 나도 새 거래로 세지 않는다(중복 집계 방지).

**청산**(두 매수 가정 모두 **t+5 영업일의 종가까지**. ①은 매수 다음 날부터 5영업일, ②는 매수일 t+1을 1일째로 세어 5영업일)
- **익절 +6.5%**: 일중 고가가 목표가에 닿으면 **목표가 그대로** 체결(갭 상승 보너스는 주지 않는다, 보수적).
- **손절 -3.0%**: 일중 저가가 손절가에 닿으면 체결하되, 시가가 이미 손절가 아래(갭 하락)면 **시가**로 체결한다.
- **같은 날 익절과 손절이 모두 닿으면 손절**로 본다(일봉으로는 순서를 알 수 없어 보수적).
- 둘 다 안 닿으면 5영업일째 종가로 정리한다.
- 목표·손절 가격은 앱의 `orders.DEFAULT_*_RATIO`(1.065, 0.97)와 같은 식(`int(price x ratio)`)으로 계산한다.

**비용**: 앱 설정의 매수 수수료, 매도 수수료, 매도 세금을 반영한다(`fees` 함수와 같은 계산). 슬리피지는 기본 0%이고 민감도로 0.1%, 0.3%를 돌린다.

## 6. 지표와 보고서

"타당한가"를 보려면 성적 숫자만으로는 부족하고, **이 필터가 아무렇게나 고르는 것보다 나은가**를 함께 본다.

**기본 성적**(매수 가정 2개 x 예산 구간 3개 각각, 그날의 추천 3개 기준)
- 거래 수, 승률(익절·손절·만료 비율), 평균 이익·평균 손실, 비용 반영 거래당 기대 손익(%), 손익비, 평균 보유일.
- 최대 낙폭: 거래를 신호일 순으로 늘어놓고 거래마다 순수익률(%)을 그대로 더한 누적 곡선에서 고점 대비 가장 크게 내려간 폭(%p). 겹치는 거래와 투자 금액을 반영하지 않으므로 계좌 낙폭이 아니다. 최대 연속 손실: 순수익률이 0보다 작은 거래가 이어진 최대 횟수. 두 정의를 보고서에 명시한다.

**타당성 비교**
- **대조군**: **전략이 신호를 낸 날에만**, 그날 추천 개수(최대 3)와 같은 수를 같은 후보 풀에서 무작위로 골라 같은 규칙으로 청산한 성적(20회 반복해 평균, 시드 고정). 신호가 없는 날에는 사지 않으므로 시장 상황 타이밍 효과가 비교에서 빠진다. 필터 통과 종목이 이보다 낫지 않으면 점수 조건에 의미가 없다는 신호다.
- **점수대별**: 60-64점 / 65-69점 / 70점 이상으로 나눠, 점수가 높을수록 실제로 더 나은지 본다.
- **시장 대비**: 같은 보유 기간의 KODEX 200(`069500`) 수익률과 비교(보조).
- **시장 상태별**: KODEX 200이 20일선 위인 날과 아래인 날로 나눈 성적. 오늘처럼 신호가 적은 약세장에서 규칙이 어땠는지 본다.
- **연도별**: 연도마다 거래 수·기대 손익·승률. 몇 해에만 기대는지, 과반의 해에서 플러스인지 본다.

**민감도**: 익절 5.2 / 6.5 / 7.8%, 손절 2.4 / 3.0 / 3.6%, 보유 3 / 5 / 7일의 격자 표(규칙값이 뾰족한 한 점인지 안정된 구간인지), 슬리피지 0 / 0.1 / 0.3%.

**판정 방식**: 단정하지 않는다. `backtest-expert`의 기준을 참고한 **점검표**(거래 100건 이상, 플러스 연도 비율, 대조군 대비 우위, 슬리피지 후 생존)로 증거를 정리해 보여 주고 결론은 사용자가 내린다. 보고서에 "투자 조언이 아니며 과거 성적이 미래 수익을 보장하지 않는다"를 적는다.

**출력**: `backtest/results/<날짜>/` 아래 `report.md`, `trades.csv`, `metrics.json`. 기본은 커밋하지 않고, 필요하면 보고서만 따로 커밋한다.

## 7. 데이터 품질

- **분할 구간**: 해당 봉에 거래가 있고 직전 20봉 내내 가격이 이어지는데(|등락| ≤ 35%), 해당 봉과 앞 20봉의 거래량 수준(0이 아닌 값의 중앙값)이 같은 방향으로 10배 이상 달라지고 뒤 20봉 수준도 그대로 이어지면 분할로 본다(분할은 영구적이라, 며칠 뛰었다 가라앉는 급등과 그 끝은 분할이 아니다). **그 앞뒤 6영업일**(거래량 5일 평균 창이 걸리는 기간)은 신호에서 제외하고, 마지막 분할 이전 기간은 후보 풀에서 뺀다.
- **거래정지일**(거래량 0)과 **가격이 0 이하인 행**(시가·고가·저가·종가 중 하나; 실데이터에 거래량은 있고 시가·고가·저가만 0인 행이 있다): 매수·청산이 불가능한 날로 처리한다. 그 날은 신호 후보에서 빠지고, 청산 판단도 건너뛴다.
- 일봉이 60개 미만이거나 받기 실패한 종목은 제외하고, **종목별 제외일 수와 실패 종목 목록**을 보고서 표로 남긴다.
- 삼성전자 한 종목에서만 분할을 확인했다. 다른 종목에서 이상이 더 나올 수 있고 배당 조정은 확인하지 않았다. 이 한계도 보고서에 적는다.
- 네이버 일봉 API는 비공식이다. 차단되면 받은 데이터까지만 쓰고 실패를 알린다.

## 8. 테스트(TDD)

시뮬레이터가 핵심이라 **손으로 만든 작은 일봉**으로 검증한다. 네트워크는 테스트에서 쓰지 않는다.

- 시뮬레이터: 익절 먼저 / 손절 먼저 / 같은 날 둘 다 / 갭 하락 손절 / 갭 상승 익절 / 5일 만료 / 수수료·세금 계산 / 다음날 시가 진입 / 중복 신호 제외 / 거래정지일 처리.
- 후보 풀: 가격 범위, 거래대금 조건, 앞 30개 자르기, 시총 순서.
- 신호: **앱의 `analyze_stock_for_swing`을 같은 입력(60봉 창, 같은 `current_price`)으로 직접 불러 결과가 같은지** 확인하는 일치 테스트(앱과 어긋나지 않는다는 보장).
- 데이터: 분할 탐지(삼성전자 2018 구간을 본뜬 작은 예), 거래정지 표시.
- 보고서 지표: 승률·기대 손익·손익비·최대 낙폭을 작은 예에서 손계산과 비교, 대조군은 고정 시드로 재현되는지.
- 병렬 실행 결과가 순차 실행과 같은지.

## 9. 실행과 운영

`python -m backtest.run`으로 한 번에 실행한다. 첫 실행은 네이버에서 일봉을 종목당 한 번(약 300번) 받고 몇 분 계산한다. 이후에는 캐시로 오프라인 재실행된다. 중단 후 이어 받기를 지원한다. 사용자 PC에서만 돌고 운영 서버와 무관하다.

## 10. 열린 위험

- 오늘 목록을 쓰는 생존 편향과 시총 순위 불일치로 결과가 실제보다 좋게 나올 수 있다. 수치를 해석할 때 이 방향의 편향임을 감안한다.
- 일봉으로는 장중 신호(앱의 실제 사용)와 같은 날 익절·손절 순서를 알 수 없어 보수적으로 가정한다.
- 12년 중 시장 국면 수가 적으면 연도별 결과가 불안정할 수 있다. 표본이 작은 구간은 보고서에 표시한다.
- 이 도구의 결과는 전략을 고칠지 판단하는 **근거 자료**이고, 그 자체로 앱 동작을 바꾸지 않는다. 전략 변경은 결과를 보고 별도 설계와 승인으로 진행한다.
