# 스윙 추천 개선 후보 검증 설계

작성일 2026-11-03 · 브랜치 `feat/backtest-improve`(PR #31 `feat/backtest-analysis` 끝에서 분기, 설계 문서 먼저, 구현은 승인 뒤)

## 1. 목적과 사용자 결정

2026-11-03 검증 분석(PR #31)은 현재 규칙이 과거 12년에서 **비용 뒤 기대값이 마이너스**이고(거래당 약 -0.2~-0.4%), 비용을 빼기 전에도 평균이 마이너스 근처이며, 요소 6개와 앱 점수 어느 것도 학습·검증 두 기간에서 평균 손익을 뒷받침하지 못한다는 것을 보였다. 이번 단계는 **개선 후보를 같은 도구로 과거 데이터에서 시험**해 어느 것이 정말 나은지 통계적으로 가린다. 이것은 **검증 단계**이며 앱 코드를 바꾸지 않는다. 합격 후보가 나와도 `strategy.py`에 반영하는 것은 결과를 본 뒤 사용자 승인과 별도 설계가 필요하다.

| 결정 | 내용 |
|---|---|
| 시험할 방향 | ① 시장 필터 ② 손절·익절·보유 기간 재설계 ③ 새 신호(추천 순위 방식). 사용자가 세 방향 모두 선택 |
| 접근 | **A: 후보 사전 등록 → 학습 기간에서 방향마다 1개 선별 → 검증 기간에서 딱 한 번 평가**. (B 워크포워드는 합격 후보가 나온 뒤 확인용으로만 고려, C 전수 격자 탐색은 과적합 위험으로 제외) |
| 개선 기준 | 사용자 결정: **검증 기간에서 비용 뒤 거래당 기대값이 0보다 크고, 동시에 KODEX 200 보유보다 낫다** |
| 판정 단계 | 합격 / 유망 / 불합격 3단계(사용자 동의). "유망"은 앱 반영 근거가 아니라 다음 시험의 출발점 |
| 코드 범위 | 새 `backtest/improve/` 폴더만. `strategy.py`·`backend/`는 import만(수정 없음). 기존 `backtest/`·`backtest/analysis/`는 수정하지 않고 재사용 |
| 결과물 | 로컬 보고서(`backtest/results/`, 커밋 제외) |

범위 밖: `strategy.py`·앱 변경, 후보 추가·변경(시험 도중), 검증 기간 결과를 본 뒤의 재조정, 워크포워드 최적화, 화면·서버 API, 실거래 연동.

## 2. 출발점 (PR #31 로컬 보고서, 2026-11-03)

| 항목 | 값 |
|---|---|
| 거래당 순손익(예산 200,000원, 다음날 시가 진입, 슬리피지 0.1%) | 약 -0.34% (수수료·세금 0.23%p 포함, 비용 전 약 -0.11%) |
| 시장 상태별(신호일 KODEX 200 종가 vs 20일선) | 위 -0.21%, 아래 -0.53% |
| 계좌 곡선 | 전액 매일 재투자 가정에서 연 -25%, KODEX 200 보유 연 +14% |
| 변동성(`atr_pct`) | 순서상 유의하나 평균 손익 근거 없음("순서만 유의") |
| 3종목 모두 손절된 날 | 15% (독립 가정 8%) |

이 후보 검증은 위 숫자를 **기준선**으로 삼는다. 기준선은 같은 시나리오(아래 3절)에서 현재 앱 규칙(점수 60 이상 상위 3, 손절 -3%, 익절 +6.5%, 5거래일)을 다시 돌린 값이다.

## 4. 후보 8개 사전 등록 (시험 중 변경·추가 금지)

모든 후보는 코드의 레지스트리(`candidates`)에 이 표 그대로 등록하고, 설계서와 어긋나면 테스트가 실패한다.

**방향 ① 시장 필터** — 추천 규칙은 그대로, 조건이 안 맞는 날은 그날 추천을 전부 비운다.
| 후보 | 조건 |
|---|---|
| F1 | 신호일 KODEX 200(`069500`) 종가 ≥ 신호일 기준 20일 단순이동평균. 벤치마크의 20봉이 안 쌓인 날은 "조건 불충족"으로 본다 |

**방향 ② 손절·익절·보유** — 추천 규칙은 그대로, `simulate_trade`의 인자만 바꾼다(`stop_ratio`, `target_ratio`, `hold_days`).
| 후보 | 손절 | 익절 | 보유 |
|---|---|---|---|
| E1 | -5% (`stop_ratio` 0.95) | +6.5% (기본값) | 5거래일 |
| E2 | -5% | +10% (`target_ratio` 1.10) | 10거래일 |
| E3 | -7% (`stop_ratio` 0.93) | +15% (`target_ratio` 1.15) | 20거래일 |

**방향 ③ 새 신호** — 앱 점수 대신 같은 후보 풀 안에서 아래 기준으로 순위를 매겨 상위 3개를 고른다. 점수 60 이상 조건은 쓰지 않는다. 후보 풀·거래정지·`vol_break` 제외·1주 이상 살 수 있는지(`calculate_position_sizing`이 None이 아님)는 기존 `evaluate`와 같은 규칙을 적용한다. 순위가 같으면 후보 풀 순서를 유지한다.
| 후보 | 조건 → 순위 |
|---|---|
| S1 상대강도 | 순위 키 = (종가_t / 종가_{t-20} - 1) - 같은 기간 KODEX 200 수익률, **큰 순** |
| S2 신고가 돌파 | 조건: 종가_t ≥ 직전 20거래일(t-20..t-1) 고가의 최댓값. 통과한 종목을 거래량 비율(`vol_ratio`)이 **큰 순** |
| S3 눌림 반등 | 조건: 종가_t ≥ 60일 단순이동평균. 통과한 종목을 5일 수익률(종가_t / 종가_{t-5} - 1)이 **낮은 순** |
| S4 저변동 | 순위 키 = ATR14 / 종가(`atr_pct`), **낮은 순** |

### 후보의 근거 강도 (정직한 표기)
| 후보 | 근거 | 강도 |
|---|---|---|
| F1 | PR #31에서 20일선 위 -0.21% vs 아래 -0.53%(전체 기간으로 본 것) | 중 |
| E1~E3 | 기준선 민감도 격자(전체 기간)에서 손절을 넓히고 오래 들수록 덜 나빴음. 5%/7%, 10일/20일은 임의의 대표 지점 | 약~중 |
| S4 | 변동성이 순서상 유의했으나 평균 근거는 없었음 | 약 |
| S1~S3 | 일반적으로 알려진 아이디어를 선택한 가설. 이 데이터·PDF·저장소에서 나온 것이 아니며 한국 시장에서의 효과는 확인 못 함 | 약 |

F1과 E1~E3와 S4는 **이미 전체 기간 결과를 본 뒤 고른 것**이라 검증 기간에 대한 완전한 사전 가설이 아니다. 보고서에 이 점을 적는다. 근거 없이 넣었던 F2(60일선), F3(20일선 기울기), E4(익절 없는 시간 청산)는 사용자와 합의해 제외했다.

## 5. 학습 선별과 검증 흐름

**5.1 학습 단계**(검증 기간 데이터를 쓰지 않는다).
1. 기준선과 후보 8개를 3절 조건으로 돌리고, 학습 기간(엠바고 제외) 거래의 **거래당 순손익 평균**을 계산한다. 구간은 날짜 블록 부트스트랩으로 같이 적는다.
2. 방향마다 평균이 가장 높은 후보 1개를 뽑는다(동률이면 레지스트리 순서). 그 평균이 **기준선의 학습 평균보다 낮거나 같으면 그 방향은 "후보 없음"**으로 접는다.
3. 뽑힌 방향이 둘 이상이면 **조합 후보 1개**를 만든다: 뽑힌 신호(③이 없으면 기존 앱 점수) → 뽑힌 필터(①) 적용 → 뽑힌 손절·익절·보유(②) 적용. 조합은 학습 단계에서 평가하지 않고 선별에도 쓰지 않는다.
4. 선별 결과와 검증에 쓸 후보 목록, 검증 후보 수 `N`(뽑힌 후보 + 조합, 최대 4)을 `selection.json`에 잠근다.

**5.2 검증 단계**(잠긴 후보만, 딱 한 번).
- 기준선과 잠긴 후보 `N`개를 검증 기간(2022-01-01 ~)에서 평가한다.
- 후보마다 아래 세 가지를 구한다(모두 검증 기간, 같은 시나리오).
  1. **거래당 순손익 평균**과 날짜 블록 부트스트랩 점추정·95% 구간·p값(`bootstrap_sums`, 날짜별 합계 `[순손익 합, 거래 수]`).
  2. **KODEX 200 보유 대비 연환산 초과수익**: 계좌 일간 수익률(`portfolio_daily`)에서 KODEX 200 계속 보유 일간 수익률을 뺀 값의 평균 x 252, 부트스트랩(`excess_ci`).
  3. **기준선 대비 연환산 초과수익**: 후보 계좌 - 기준선 계좌(`excess_ci`).
- 참고용으로 같은 기간 연수익·최대 낙폭·샤프·시장 노출, KODEX 200 같은 날만 보유 대비 초과수익, 예산 100,000원과 500,000원 구간의 거래당 순손익을 보고서에 적는다(판정에는 쓰지 않는다).

## 6. 판정

보정 기준 `alpha_adj = 0.05 / N`(N = 5.1의 검증 후보 수). 아래의 "유의"는 `점추정 > 0` 이고 `p ≤ alpha_adj`(분석 층 `BootResult.p`는 양쪽 검정 p이므로 방향을 따로 확인)인 경우다.

| 판정 | 조건 |
|---|---|
| **합격** | 5.2의 ① 거래당 순손익이 유의 **그리고** ② KODEX 200 보유 대비 초과수익이 유의 |
| **유망** | 합격이 아니고, ③ 기준선 대비 초과수익이 유의 |
| **불합격** | 위 둘 다 아님 |

- 합격이어도 "앱 반영 근거"가 아니라 "앱 반영을 논의할 후보"이며, 보고서에 한계와 함께 적는다. 유망은 "다음 시험의 출발점"이라고 명시한다.
- 후보가 하나도 선별되지 않으면(모든 방향이 접힘) 결과는 "개선 후보 없음"이며 그 자체를 결론으로 보고한다.
- 불합격이 "효과가 없다"는 뜻이 아니라는 문장을 보고서에 넣는다(표본·검정력 한계).

## 7. 단계 잠금(검증 기간을 한 번만 쓰는 장치)

실행은 두 단계로 나뉜다. `python -m backtest.improve.run --stage train`이 선별 결과를 출력 폴더의 `selection.json`에 쓰고, `--stage test`는 `selection.json`이 있을 때만 그 후보를 평가해 `test_result.json`을 쓴다.
- `selection.json`이 없으면 test는 거부한다.
- `test_result.json`이 이미 있으면 `--allow-rerun` 없이는 거부한다. 재실행하면 결과에 `rerun: true`를 기록하고 보고서 맨 앞에 "검증 기간을 재사용함(결과 신뢰도 하락)" 배너를 넣는다.
- `selection.json`에는 후보 목록, 학습 평균, 시드, 저장소 커밋 해시(알 수 있을 때)를 기록한다.
- 이 장치는 실수로 검증 기간을 재사용하는 것을 막고 기록으로 남기는 용도이며, 파일을 일부러 지우는 것까지 막지는 못한다.

## 8. 구성

| 조각 | 하는 일 |
|---|---|
| `candidates.py` | 4절 레지스트리(이름·방향·인자) 고정 |
| `ranking.py` | S1~S4 순위를 일봉으로 계산해 기존 `DayResult`/`Signal` 모양(후보 풀 + 정렬된 추천)으로 만든다. `Signal.score`는 순위(1부터)를 담는다 |
| `filters.py` | F1: 허용되지 않는 날의 `signals`를 비운다(풀은 유지) |
| `evaluate.py` | 후보 하나를 3절 조건으로 돌려 거래 → 학습/검증 분할(엠바고 포함) → 5.2의 통계. `backtest.analysis.bootstrap`, `equity`, `features`를 재사용 |
| `select.py` | 5.1의 선별·조합 규칙과 `selection.json` |
| `judge.py` | 6절 판정 |
| `report.py`, `run.py` | 보고서와 `--stage` CLI. 기준선 신호는 `backtest.run`의 병렬 신호 생성을 재사용(예산 200,000원 한 번) |

기준선 신호 생성은 한 번만 하고(예산 200,000원), 방향 ①②는 그 결과를 재사용하며, ③은 앱 점수 계산이 필요 없어 가볍다. 실제 소요 시간은 실측 전이다(확인 못 함).

## 9. 보고서와 한계

보고서는 한계를 결과보다 먼저 쓴다. 반드시 들어갈 한계:
- 후보 풀이 오늘의 시총 목록이라 **생존 편향**(결과가 실제보다 좋게 나오는 쪽).
- 일봉이라 장중 움직임을 못 보고 계좌 낙폭이 낙관적이다.
- 후보 8개는 근거가 약한 가설이며, F1·E1~E3·S4는 이미 전체 기간 결과를 본 뒤 골랐다.
- 학습에서 8개 중 방향별 최고를 골랐으므로 학습 성적은 낙관적이고, 검증 한 번이 판정의 근거다. 검증 기간(2022~)은 약 5년이다.
- 시험 횟수 보정은 검증 후보 수 `N`에만 적용했고, 학습 단계의 8개 비교는 보정하지 않았다(검증이 새 데이터이므로).
- 연수익은 전액 매일 재투자 가정이다. 불합격은 효과가 없다는 뜻이 아니다.

결과 표현: 학습 표(기준선 포함 9행: 거래 수, 거래당 평균, 구간, 선별 여부), 검증 표(N+1행: 세 가지 통계, p값, `alpha_adj`, 판정), 참고용 표, 한계.

## 10. 테스트 방침

- **사전 등록 가드:** 레지스트리가 4절 목록(이름·방향·인자)과 정확히 같다.
- **S1~S4:** 손으로 계산한 작은 일봉에서 순위·조건이 일치, 날짜 t 이후 데이터를 바꿔도 t의 순위 불변, 후보 풀 밖 종목·거래정지·`vol_break`·살 수 없는 종목 제외, 동률은 풀 순서.
- **F1:** 조건이 맞는 날만 추천이 남고 나머지는 비어 있다, 20봉 미만인 날은 조건 불충족.
- **E1~E3:** 인자가 `simulate_trade`로 전달돼 손절·익절·만료 가격이 기대대로 나온다.
- **엠바고:** 학습 마지막 20거래일 신호가 학습 집계에서 빠지고 검증 집계에는 영향이 없다.
- **선별:** 방향별 최고 선택, 기준선보다 나쁘면 접힘, 동률은 등록 순서, 조합 구성(신호→필터→청산), 방향이 하나뿐이면 조합을 따로 만들지 않아 N이 중복되지 않는다.
- **판정:** 합격/유망/불합격 경계, `alpha_adj = 0.05/N`, 방향이 음수이면 p가 작아도 유의가 아니다, 후보 없음 처리.
- **단계 잠금:** selection 없으면 test 거부, 두 번째 test 거부, `--allow-rerun`은 배너와 `rerun: true`.
- **통합:** 합성 종목으로 train → test가 끝까지 돌고 보고서에서 한계가 결과보다 앞에 오며, 일봉을 받지 않는다.
- 기존 테스트(1,297개)는 그대로 통과해야 한다. 앱 코드 변경이 없어 프론트 문법검사는 해당 없음.

## 11. 열린 항목 (구현 계획에서 정할 것)

- 소요 시간은 실측 전(확인 못 함). 계획 단계에서 한 번 재서 병렬 처리 필요 여부를 정한다.
- S2의 "직전 20거래일 고가" 계산에서 거래정지 행(고가 0 이하)은 건너뛴다. 세부 처리는 계획에서 테스트로 고정한다.
- 합격 후보가 나오면 워크포워드(접근 B) 확인과 앱 반영 설계는 별도 단계로 다룬다.
