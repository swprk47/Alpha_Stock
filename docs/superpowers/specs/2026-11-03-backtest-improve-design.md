# 스윙 추천 개선 후보 검증 설계

작성일 2026-11-03 · 리뷰 반영 2차본 · 브랜치 `feat/backtest-improve`(PR #31 `feat/backtest-analysis` 끝에서 분기, 설계 문서 먼저, 구현은 승인 뒤)

## 1. 목적과 사용자 결정

2026-11-03 검증 분석(PR #31)은 현재 규칙이 과거 12년에서 **비용 뒤 기대값이 마이너스**이고(거래당 약 -0.2~-0.4%), 비용을 빼기 전에도 평균이 마이너스 근처이며, 요소 6개와 앱 점수 어느 것도 학습·검증 두 기간에서 평균 손익을 뒷받침하지 못한다는 것을 보였다. 이번 단계는 **개선 후보를 같은 도구로 과거 데이터에서 시험**해 어느 것이 정말 나은지 통계적으로 가린다. 이것은 **검증 단계**이며 앱 코드를 바꾸지 않는다. 합격 후보가 나와도 `strategy.py`에 반영하는 것은 결과를 본 뒤 사용자 승인과 별도 설계가 필요하다. **이 결과는 투자 권유가 아니며, 이 결과만으로 실계좌 규칙을 바꾸면 안 된다.**

| 결정 | 내용 |
|---|---|
| 시험할 방향 | ① 시장 필터 ② 손절·익절·보유 기간 재설계 ③ 새 신호(추천 순위 방식). 사용자가 세 방향 모두 선택 |
| 접근 | **A: 후보 사전 등록 → 학습 기간에서 방향마다 1개 선별 → 검증 기간에서 딱 한 번 평가**. (B 워크포워드는 합격 후보가 나온 뒤 확인용으로만 고려, C 전수 격자 탐색은 과적합 위험으로 제외) |
| 개선 기준 | 사용자 결정: **검증 기간에서 비용 뒤 거래당 기대값이 0보다 크고, 동시에 KODEX 200 보유보다 낫다** |
| 판정 단계 | 합격 / 유망 / 불합격 3단계(사용자 동의). "유망"은 앱 반영 근거가 아니라 다음 시험의 출발점 |
| 후보 | 8개(근거 약한 F2, F3, E4는 사용자와 합의해 제외) |
| 코드 범위 | 새 `backtest/improve/` 폴더만. `strategy.py`·`backend/`는 import만(수정 없음). 기존 `backtest/`·`backtest/analysis/`는 수정하지 않고 재사용 |
| 결과물 | 로컬 보고서(`backtest/results/`, 커밋 제외) |

범위 밖: `strategy.py`·앱 변경, 후보 추가·변경(시험 도중), 검증 기간 결과를 본 뒤의 재조정, 워크포워드 최적화, 화면·서버 API, 실거래 연동.

## 3. 공통 시험 조건

| 항목 | 값 |
|---|---|
| 예산 구간(합격 판정에 쓰는 유일한 구간) | **200,000원**. 10만·50만 원 구간은 선별된 후보에 대해서만 확인용으로 계산하고 판정에 쓰지 않는다 |
| 진입 | 다음날 시가, 슬리피지 0.1%(진입·청산 각각), 수수료·세금은 `fees` |
| 후보 풀 | 기존 규칙 그대로(`select_pool`, 시총 순 앞 30개, 가격·거래대금 조건, 거래정지·분할 제외) |
| 추천 | 신호일마다 순위 순서 상위 3개(`daily_picks`) |
| **판정용 계좌 = 슬롯 제한 계좌 (K=2, 사전 등록)** | 앱 사이징이 종목당 예산의 50%(`max_allocation_ratio` 0.5)를 배정하므로 실제 동시 보유는 약 2종목이다. 신호일 d에 추천 상위 3개를 순위 순서로 훑어, ① 이미 보유 중인 종목이거나 ② `exit_date > d`인 보유 거래가 이미 K개이면 건너뛰고, 아니면 거래를 연다(d의 상태만 쓰므로 미래 정보 없음). 계좌 일간 수익률 = 그날 열린 포지션들의 일간 수익률 합 / K (빈 슬롯은 현금 0%, 매일 1/K로 재조정). **거래당 통계도 이 계좌가 실제로 낸 거래만 쓴다.** 기준선(현재 규칙)도 똑같이 K=2로 다시 측정한다 |
| 기간·경계 | **학습**: 일봉 프레임을 `TRAIN_END`(2021-12-31)에서 잘라 실행한다. 그러면 청산일이 TRAIN_END 이하인 거래만 존재해 구조적으로 검증 기간과 겹치지 않는다(별도 20일 엠바고 규칙을 두지 않는다). **검증**: 신호일 ≥ 2022-01-01 이고 신호일 ≤ `test_end`. `test_end` = 전체 종목 합집합 거래일 달력의 마지막 날에서 20거래일 앞(최대 보유일 20과 맞춘, 모든 후보와 기준선 공통의 끝. 긴 보유 후보만 데이터 끝에서 미완결로 잘려 현금이 되는 불공정을 없앤다). 계좌 일간 수익률의 창 = 2022-01-01 이후 첫 거래일 ~ `test_end` |
| 날짜별 합계 행 | 위 창 안의 **모든 거래일**을 행으로 두고(거래가 없는 날은 0 행) 부트스트랩에 넣는다 |
| 부트스트랩 | 날짜 블록 **20거래일**(최대 보유일 20에 맞춰 모든 후보·기준선·학습·검증에 동일), 판정에 쓰는 통계는 재추출 **20,000회**(p 문턱 근처의 몬테카를로 오차를 줄이기 위해), 시드 20261103. 분석 층의 `excess_ci`는 block 인자가 없어 쓰지 않고 `bootstrap_sums`를 직접 호출한다 |
| 미래 정보 | 날짜 t의 모든 판단(순위·필터)은 t까지의 일봉만 쓴다. 진입은 t+1 시가. "t-20" 같은 행 오프셋은 각 종목(KODEX 포함)의 **자기 프레임 행** 기준이다 |

## 4. 후보 8개 사전 등록 (시험 중 변경·추가 금지)

모든 후보는 코드의 레지스트리(`candidates`)에 이 표 그대로 등록하고, 설계서와 어긋나면 테스트가 실패한다.

**방향 ① 시장 필터** — 추천 규칙은 그대로, 조건이 안 맞는 날은 그날 추천을 전부 비운다.
| 후보 | 조건 |
|---|---|
| F1 | 신호일 KODEX 200(`069500`) 종가 ≥ 신호일 기준 20일 단순이동평균. 벤치마크에 신호일 행이 없거나 20봉이 안 쌓인 날은 "조건 불충족"으로 본다 |

**방향 ② 손절·익절·보유** — 추천 규칙은 그대로, `simulate_trade`의 인자만 바꾼다(`stop_ratio`, `target_ratio`, `hold_days`).
| 후보 | 손절 | 익절 | 보유 |
|---|---|---|---|
| E1 | -5% (`stop_ratio` 0.95) | +6.5% (기본값) | 5거래일 |
| E2 | -5% | +10% (`target_ratio` 1.10) | 10거래일 |
| E3 | -7% (`stop_ratio` 0.93) | +15% (`target_ratio` 1.15) | 20거래일 |

**방향 ③ 새 신호** — 앱 점수 대신 같은 후보 풀 안에서 아래 기준으로 순위를 매겨 상위 3개를 고른다(이후 슬롯 규칙은 3절). 점수 60 이상 조건은 쓰지 않는다. 거래정지·`vol_break` 행은 기존 `evaluate`와 같이 제외한다. (가격이 예산 이하인 풀 종목은 항상 1주 이상 살 수 있어 `calculate_position_sizing`이 None이 되지 않지만, `evaluate`와 일관되게 같은 검사를 유지한다.) 순위가 같으면 후보 풀 순서를 유지한다. 필요한 값이 없거나 계산할 수 없으면(자기 프레임 행 부족, 해당 종가 0 이하, `halt` 행, NaN) 그 종목은 그날 **제외**하고, 통과 종목이 3개 미만이면 그만큼만 추천한다. `Signal.score`는 0, `risk_reward`는 0.0으로 두고 순위는 별도 딕셔너리에 담는다(점수 기반 집계가 순위를 점수로 오인하지 않게).
| 후보 | 조건 → 순위 |
|---|---|
| S1 상대강도 | 순위 키 = (종가_t / 종가_{t-20} - 1) - (KODEX 200의 같은 20행 수익률), **큰 순**. 종목과 KODEX의 t와 t-20행 종가가 모두 양수여야 한다 |
| S2 신고가 돌파 | 조건: 종가_t ≥ 직전 20행(t-20..t-1)에서 `halt` 행을 뺀 나머지의 고가 최댓값(남은 행이 15개 미만이면 제외). 통과 종목을 거래량 비율(`vol_ratio`)이 **큰 순** |
| S3 눌림 반등 | 조건: 60일 단순이동평균이 존재하고 종가_t ≥ 그 값. 통과 종목을 5일 수익률(종가_t / 종가_{t-5} - 1)이 **낮은 순** |
| S4 저변동 | 순위 키 = ATR14 / 종가(`atr_pct`, NaN 제외), **낮은 순** |

### 후보의 근거 강도 (정직한 표기)
| 후보 | 근거 | 강도 |
|---|---|---|
| F1 | PR #31에서 20일선 위 -0.21% vs 아래 -0.53%(전체 기간으로 본 것) | 중 |
| E1~E3 | 기준선 민감도 격자(손절 2.4~3.6%, 보유 3~7일, 익절 5.2~7.8%, 전체 기간)에서 격자 안에서는 손절을 넓히고 오래 들수록 덜 나빴다. **E1~E3의 값(5%/7%, 10일/20일, 10%/15%)은 격자 바깥으로 외삽한 임의의 대표 지점**이다. 또 보유가 길수록 거래당 평균이 시장 드리프트를 더 담는 편향이 있어 5.1에서 KODEX 대비로 보정한다 | 약 |
| S4 | 변동성이 순서상 유의했으나 평균 근거는 없었음 | 약 |
| S1~S3 | 일반적으로 알려진 아이디어를 선택한 가설. 이 데이터·PDF·저장소에서 나온 것이 아니며 한국 시장에서의 효과는 확인 못 함 | 약 |

**사전 노출 표시:** F1, E1~E3, S4(그리고 이를 포함한 조합)는 **검증 기간이 포함된 전체 기간 결과를 본 뒤 고른 것**이라, 그 검증은 완전히 새로운 데이터에 대한 검정이 아니다. 보고서의 판정 칸에 "(검증 기간 사전 노출)"을 강제로 붙이고, 합격이어도 "새 데이터(앞으로의 구간 또는 별도 표본)로 다시 확인하기 전에는 앱 반영 논의 대상이 아니다"라고 적는다. S1~S3은 이번 데이터에서 본 적 없는 아이디어이다.

## 5. 학습 선별과 검증 흐름

**5.1 학습 단계**(프레임을 `TRAIN_END`에서 잘라 실행하므로 검증 기간 데이터를 구조적으로 쓸 수 없다).
1. 기준선과 후보 8개를 3절 슬롯 제한 계좌로 돌린다.
2. **선별 지표 = 거래당 (순손익 - 같은 진입·청산 구간의 KODEX 200 수익률)의 평균.** 보유가 길수록 거래당 절대 평균이 시장 드리프트를 더 담는 편향(E3가 실력과 무관하게 유리해짐)을 없애기 위해서다. KODEX 구간 수익률은 기존 `benchmark_excess`와 같다(다음날 시가 진입이면 진입일 시가 → 청산일 종가). 날짜 블록(20) 부트스트랩 구간을 같이 적는다. 보고서에 거래당 절대 순손익, 거래 수, 평균 보유일, 시장 노출(보유 포지션이 있는 날 비율)도 함께 적는다.
3. 방향마다 선별 지표가 가장 높은 후보 1개를 뽑는다(동률이면 레지스트리 순서). 그 값이 **같은 방식으로 잰 기준선의 학습 값보다 낮거나 같으면 그 방향은 "후보 없음"**으로 접는다.
4. **조합:** 뽑힌 방향이 둘 이상이면 조합 후보(뽑힌 신호 → 뽑힌 필터 → 뽑힌 청산; ③이 없으면 기존 앱 점수)를 만들고 **학습 단계에서도 평가**한다. 조합의 선별 지표가 뽑힌 단일 후보들의 최댓값을 넘을 때만 검증 후보에 넣는다(학습 데이터만 쓰는 결정). 아니면 조합은 만들지 않는다.
5. **N = 검증 후보 수** (뽑힌 단일 후보 + 포함된 조합, 최대 4). 학습 데이터만으로 정해지므로 검증 결과가 N에 새지 않는다.
6. **최소 검출 효과(MDE) 추정:** 학습 기준선의 거래당 순손익 부트스트랩 표준오차를 `sqrt(학습 일수 / 검증 일수)`로 환산한 값을 `SE_test`라 하고 `MDE = (z_{1-0.05/N} + z_{0.80}) x SE_test`(정규 근사)를 계산해 `selection.json`과 보고서 앞부분에 적는다("검증 기간에서 거래당 순손익이 대략 이만큼 이상 좋아야 ①이 유의해질 수 있다"). 추정치이며 확정이 아니다.
7. 위 결과와 검증 후보 목록, N, 시드, 데이터 스냅샷 정보를 `selection.json`에 잠근다(7절).

**5.2 검증 단계**(잠긴 후보만, 딱 한 번). 기준선과 잠긴 후보 N개를 3절의 검증 경계에서 평가한다. 모두 슬롯 제한 계좌 기준이다.
1. **거래당 순손익 평균(절대)** — 점추정·95% 구간·p. 날짜별 합계 `[순손익 합, 거래 수]`의 비율 통계(`bootstrap_sums`, 블록 20, 20,000회).
2. **KODEX 200 보유 대비 계좌 로그성장 초과** — 일별 `log(1 + 후보 계좌 수익률) - log(1 + KODEX 200 일간 수익률)`의 평균 x 252. 산술 평균 초과는 변동성이 큰 집중 계좌의 복리 성과를 과대평가하므로 로그 차이를 쓴다. KODEX 200은 가격 수익률이다(분배금 미반영, 아래 한계 참조).
3. **기준선 대비 계좌 로그성장 초과** — 같은 방식, 후보 계좌 - 기준선 계좌.
4. 참고용(판정에 쓰지 않음): 연수익(기하)·최대 낙폭·샤프·시장 노출·평균 보유일, 현금 대비 로그성장 초과, KODEX 200 같은 날만 보유 대비 초과, **연도별 거래당 순손익·계좌 수익(2022~)**, 예산 100,000원과 500,000원 구간의 거래당 순손익, "KODEX 200 분배금을 연 2%p로 가정해 ②에서 뺀 경우"의 판정(가정치, 한계 참조).

## 6. 판정

- **유의 정의:** 점추정이 0보다 크고 **한쪽 p ≤ alpha_adj**. 분석 층 `BootResult.p`는 양쪽 p(`2 x min(share<=0, share>=0)`)이므로 한쪽 p는 점추정이 양수일 때 `p / 2`로 쓴다. `alpha_adj = 0.05 / N`(Bonferroni, N = 검증 후보 수). 판정 문턱의 ±20% 안이면 "경계"로 표기한다.
- ①과 ②를 모두 요구하는 합격은 교집합 검정이라 각각을 `alpha_adj`에서 보는 것이 보수적이다(이중 계산이 아님).

| 판정 | 조건 |
|---|---|
| **합격** | ① 거래당 순손익이 유의 **그리고** ② KODEX 200 보유 대비 계좌 로그성장 초과가 유의 |
| **유망** | 합격이 아니고, ③ 기준선 대비 초과가 유의 **그리고 ① 거래당 순손익 점추정 > 0 그리고 현금 대비 계좌 로그성장 초과 점추정 > 0** |
| **불합격** | 위 둘 다 아님 |

- 유망에 ①·현금 조건을 둔 이유: 기준선이 마이너스라서 거래를 덜 하기만 해도 기준선 대비 초과는 양수가 된다. 현금(아무것도 안 사기)보다 나쁜 후보가 "유망"이 되지 않게 한다. 판정 칸 옆에 시장 노출과 현금 대비 초과를 항상 같이 적는다.
- 합격이어도 "앱 반영을 논의할 후보"일 뿐이며, 4절의 사전 노출 후보는 새 데이터 확인 전까지 반영 논의 대상이 아니다. 유망은 "다음 시험의 출발점"이라고 명시한다.
- 선별된 후보가 하나도 없으면(모든 방향이 접힘) 결과는 "개선 후보 없음"이며 그 자체를 결론으로 보고한다.
- 불합격이 "효과가 없다"는 뜻이 아니라는 문장을 보고서에 넣는다(표본·검정력 한계, MDE 참조).

## 7. 단계 잠금(검증 기간을 한 번만 쓰는 장치)

실행은 두 단계로 나뉘고 출력 폴더는 **고정 경로 `backtest/results/improve/`**다(실행일 폴더를 쓰면 다음 날 실행이 "처음"이 되기 때문).
- `--stage train`: 선별 결과를 `selection.json`에 쓴다. `test_result.json`이 이미 있으면 **train도 거부**한다(검증을 본 뒤 선별을 덮어쓰는 것을 막는다).
- `--stage test`: `selection.json`이 있을 때만 그 후보를 평가해 `test_result.json`을 쓴다. 이미 `test_result.json`이 있으면 `--allow-rerun` 없이는 거부한다.
- `selection.json`에는 후보 목록, N, 학습 값과 MDE, 시드, 설정(예산 구간, 슬리피지, 진입 방식, 슬롯 수 K, 블록, 재추출 횟수), 레지스트리 해시, 데이터 스냅샷(`listing.json` 해시, 프레임 수, 첫·마지막 날짜, `test_end`), 저장소 커밋 해시와 working tree 변경 여부를 기록한다.
- test 단계는 현재 데이터 스냅샷·설정·레지스트리 해시가 `selection.json`과 다르면 거부한다(캐시를 갱신하면 검증 표본이 달라지므로). `--allow-rerun`으로 통과시키면 `test_result.json`에 `rerun: true`와 어긋난 항목을 기록하고 보고서 맨 앞에 "검증 기간 재사용 또는 데이터 변경(결과 신뢰도 하락)" 배너를 넣는다.
- `test_result.json`에는 사용한 `selection.json`의 해시를 기록한다.
- 이 장치는 실수로 검증 기간을 재사용하는 것을 막고 기록으로 남기는 용도이며, 파일을 일부러 지우는 것까지 막지는 못한다.

## 8. 구성

| 조각 | 하는 일 |
|---|---|
| `candidates.py` | 4절 레지스트리(이름·방향·인자·사전 노출 여부) 고정 |
| `ranking.py` | S1~S4 순위를 일봉으로 계산해 기존 `DayResult`/`Signal` 모양(후보 풀 + 정렬된 추천)으로 만든다. 순위는 별도 딕셔너리 |
| `filters.py` | F1: 허용되지 않는 날의 `signals`를 비운다(풀은 유지) |
| `slots.py` | 3절의 슬롯 제한 계좌: 신호 목록 → 거래 목록(`simulate_trade` 재사용, 슬롯·중복 보유 규칙), 거래 목록 → 일간 수익률(`equity.trade_daily_factors` 재사용, 합 / K) |
| `evaluate.py` | 후보 하나를 학습/검증 경계에서 평가: 거래당 KODEX 초과·절대 순손익, 계좌 로그성장 초과(vs KODEX, vs 기준선, vs 현금), 참고 지표. `bootstrap_sums` 직접 호출(블록 20) |
| `select.py` | 5.1의 선별·조합·N·MDE |
| `judge.py` | 6절 판정(한쪽 p 변환, Bonferroni, 유망 조건, 사전 노출 표시) |
| `lock.py` | 7절 단계 잠금과 스냅샷·해시 기록·검증 |
| `report.py`, `run.py` | 보고서와 `--stage` CLI. 기준선 신호는 `backtest.run`의 병렬 신호 생성을 재사용(예산 200,000원, 학습 단계는 절단된 프레임, 검증 단계는 전체 프레임으로 각각 생성) |

방향 ①②는 기준선 신호를 재사용하고, ③은 앱 점수 계산이 필요 없어 가볍다. 실제 소요 시간은 실측 전이다(확인 못 함).

## 9. 보고서와 한계

보고서의 **첫 줄**은 "이 보고서는 투자 권유가 아니며, 이 결과만으로 실계좌 규칙을 바꾸면 안 된다"이고, 한계를 결과보다 먼저 쓴다. 반드시 들어갈 한계:
- 후보 풀이 오늘의 시총 목록이라 **생존 편향**(결과가 실제보다 좋게 나오는 쪽).
- 일봉이라 장중 움직임을 못 보고, 다음날 시가·손절가 체결 가정이 낙관적이며 계좌 낙폭도 낙관적이다.
- 후보 8개는 근거가 약한 가설이며 F1·E1~E3·S4는 이미 검증 기간을 포함한 전체 기간 결과를 본 뒤 골랐다(사전 노출). E1~E3의 값은 민감도 격자 바깥으로 외삽한 대표 지점이다.
- 학습에서 방향별 최고를 골랐으므로 학습 성적은 낙관적이고, 검증 한 번이 판정의 근거다. 검증 기간(2022~2026)은 약 5년이며 2022년 약세와 이후 상승을 포함해 **국면 의존성**이 크다(F1의 효과는 국면에 달려 있다). 연도별 표를 참고로 넣는다.
- 시험 횟수 보정은 검증 후보 수 N에만 적용했고, 학습 단계의 8개 비교는 보정하지 않았다(검증이 새 데이터이므로. 단 사전 노출 후보는 예외).
- 판정용 계좌는 동시 보유 2종목(K=2), 매일 1/K 재조정, 전액 투자 가정이다. 실제 운용은 다를 수 있다.
- KODEX 200은 **가격 수익률**이라 분배금이 빠져 있다(크기는 이 데이터로 확인 못 함). 후보가 KODEX를 이기기 쉬운 쪽의 편향이며, 5.2-4의 "연 2%p 가정"은 임의의 가정치이다.
- S 후보는 점수 60 필터가 없어 거의 매일 3종목 후보가 생겨 노출과 회전이 기준선과 크게 다를 수 있다(시장 노출과 거래 수를 같이 적는다).
- 불합격은 효과가 없다는 뜻이 아니다. 검증 후보가 거래당 평균을 유의하게 바꾸려면 MDE만큼 개선돼야 한다.

결과 표현: 학습 표(기준선 포함 9행 + 조합: 거래 수, 거래당 절대·KODEX 대비 평균, 구간, 평균 보유일, 노출, 선별 여부), MDE, 검증 표(기준선 + N행: 세 가지 통계, 한쪽 p, `alpha_adj`, 경계 표시, 판정, 사전 노출 표시, 시장 노출, 현금 대비 초과), 참고용 표(연도별 포함), 한계.

## 10. 테스트 방침

- **사전 등록 가드:** 레지스트리가 4절 목록(이름·방향·인자·사전 노출 여부)과 정확히 같다.
- **S1~S4:** 손으로 계산한 작은 일봉에서 순위·조건이 일치, 날짜 t 이후 데이터를 바꿔도 t의 순위 불변, 풀 밖 종목·거래정지·`vol_break` 제외, 필요한 행이 없거나 종가가 0 이하이면 제외, 통과가 3개 미만이면 그만큼만, 동률은 풀 순서, `Signal.score`가 0이고 점수 기반 집계에 순위가 새지 않는다.
- **F1:** 조건이 맞는 날만 추천이 남고 나머지는 비어 있다, 벤치마크 행이 없거나 20봉 미만인 날은 조건 불충족.
- **E1~E3:** 인자가 `simulate_trade`로 전달돼 손절·익절·만료 가격이 기대대로 나온다.
- **슬롯 계좌:** 보유 중 종목 건너뜀, K개가 차면 그날 추천 건너뜀, 청산일이 d 이하이면 슬롯이 비어 있음, 계좌 일간 수익률 = 합 / K, 빈 슬롯은 0, 같은 거래 목록으로 거래당 통계를 계산한다. 보유가 긴 후보도 동시 보유가 K를 넘지 않는다.
- **경계:** 학습 프레임을 `TRAIN_END`에서 자르면 `TRAIN_END` 이후 데이터를 바꿔도 `selection.json`이 동일하다. 검증 창이 `test_end`에서 끝나고 모든 후보·기준선이 같은 창을 쓴다. 날짜별 합계 행에 거래 없는 날(0)이 포함된다.
- **블록·재추출:** 모든 통계가 블록 20, 20,000회를 쓴다(5가 섞이지 않는다).
- **선별:** 방향별 최고 선택(KODEX 대비 지표), 기준선보다 나쁘거나 같으면 접힘(기준선도 같은 지표), 동률은 등록 순서, 조합은 학습에서 평가되고 단일 최댓값을 넘을 때만 포함(방향이 하나뿐이면 조합 없음, N 중복 없음), MDE 계산.
- **판정:** 합격/유망/불합격 경계, `alpha_adj = 0.05/N`, 점추정이 음수이면 p가 작아도 유의가 아님, 한쪽 p 변환(`p/2`), 경계 표시, 유망의 ①·현금 조건(현금보다 나쁜 후보는 유망이 아님), 후보 없음 처리, 사전 노출 표시.
- **단계 잠금:** selection 없으면 test 거부, test 후 train 거부, 두 번째 test 거부, 스냅샷·설정·레지스트리 해시 불일치 시 test 거부, `--allow-rerun`은 배너와 `rerun: true`, `test_result.json`에 selection 해시 기록.
- **통합:** 합성 종목으로 train → test가 끝까지 돌고 보고서의 첫 줄·한계가 결과보다 앞에 오며, 일봉을 받지 않는다.
- 기존 테스트(1,297개)는 그대로 통과해야 한다. 앱 코드 변경이 없어 프론트 문법검사는 해당 없음.

## 11. 열린 항목 (구현 계획에서 정할 것)

- 소요 시간은 실측 전(확인 못 함). 계획 단계에서 한 번 재서 병렬 처리 필요 여부를 정한다.
- KODEX 200 분배금의 실제 크기는 이 데이터에 없다(확인 못 함). 5.2-4의 2%p 민감도는 임의의 가정이며, 사용자가 다른 값을 알고 있으면 바꾼다.
- 합격 후보가 나오면 워크포워드(접근 B) 확인과 앱 반영 설계는 별도 단계로 다룬다.

## 12. 리뷰 반영 이력 (1차본 → 2차본)

Opus 리뷰어의 지적을 반영했다: 판정 계좌를 슬롯 제한(K=2)으로 변경, 부트스트랩 블록을 20으로 통일, "유망"에 현금·절대 기대값 조건 추가, 선별 지표를 KODEX 대비로 변경, ②를 로그성장 초과로 변경, 검증·학습 경계와 `test_end` 정의, 학습 프레임 절단으로 구조적 엠바고, 단계 잠금 보강(고정 경로, 스냅샷·해시), 조합을 학습에서 평가, MDE 보고, 한쪽 p 사용과 재추출 20,000회, 사전 노출 표시, 한계 보강, 후보 세부 정의 명확화, 테스트 보강.
